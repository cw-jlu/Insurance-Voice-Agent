## 二、实验 1：报价全量枚举

**做法**：枚举 0–105 岁 × 有无社保 × 年缴/月缴 × 男女 × 不选或选 7 种加油包之一，共 6,784 个组合。被测报价引擎（`src/agent/quote.py`）的结果与另一套独立实现（`experiments/exp1_quote.py` 中用 pandas 写的参照实现）逐一比对；另做边界抽查、家庭单 1–6 人测试。

**结果**：

| 项目 | 结果 |
|---|---|
| 价格不一致 | **0 / 6,784** |
| 不可投保组合被正确拒绝 | 2,360 个，误报价 0 个 |
| 边界抽查（30/31 岁、70/71 岁、出生 20 天、55/56 岁门急诊加油包、重疾关爱缺性别） | 11 项全部通过 |
| 家庭单 1–6 人折扣（0/5%/10%/15%/20%/20%） | 全部通过，均标记"折扣范围和取整待确认" |
| 月缴 ×12 是否高于年缴 | 可投保年龄段 30/30 全部高于年缴 |

**发现**：费率表里有**续保价格**——必选计划有 7 个 70 岁以上的年龄段，门急诊加油包在 56–70 岁也有价格，但投保须知规定首次投保被保人不超过 70 周岁、门急诊加油包不超过 55 周岁。**如果按"表里有价就能报"来写，会给不能投保的人报价。**资格规则必须来自投保须知，费率表只负责价格。

**局限**：参照实现和被测实现由同一人编写，读的是同一份 CSV；CSV 本身的正确性由数据管线的 OCR 逐格交叉校验保证（见 [data/README.md](../data/README.md)）。

## 三、实验 3：护栏

### 3.1 做法

- **数字护栏**：以方案附录 A 的 5 个正确回答为基础，程序逐个篡改其中的数字（翻倍、加一、数字倒序），共生成 54 个错误回答，检查护栏能否拦住；同时检查正确回答是否被误拦。
- **缺口结论拦截**：针对疾病核保、续保、社保抵扣免赔额三类数据缺口，构造"违规回答"（给了结论）和"合规回答"（以核保/条款为准），检查拦截的召回率和精确率。
- **禁用表述**、**AI 身份识别**：构造正例和反例。

为了避免"对着测试题调规则"，用了三组用例：

| 用例组 | 用途 |
|---|---|
| 开发集 | 编写和调整规则 |
| 保留集 1 | v1 规则写完后才写，用来发现 v1 的泛化问题；**发现问题后参与了 v2 调整，不再算作未见数据** |
| 保留集 2 | v2 调整前写好，**调整期间未查看结果**，只用于最终评估 |

### 3.2 v1 结果：规则在新问法上明显失效

| 指标 | 开发集 | 保留集 1 |
|---|---|---|
| 数字篡改拦截率 | 87.0%（47/54） | 81.8%（36/44） |
| 缺口拦截 召回 / 精确 | 100% / 84.2% | **40% / 40%** |
| 禁用表述正确率 | 100% | **0%（0/4）** |
| AI 身份识别召回 | 85% | **30%** |

v1 的问题：

1. 数字护栏只检查"数值是否在证据里出现过"，换成另一个合法数字（一般住院 300 万 → 600 万）拦不住；证据里的列表序号"1）""6）"也被当成了可用数字。
2. "能不能投保""如果能买"这类**谨慎表述**被误判为给了结论；"血压有点高"没被识别为病史问题。
3. 禁用表述不认识否定句（"不能保证续保"被误拦），也漏掉新说法（"大病小病都能报"）。
4. 身份问题问法多样（"你该不会是机器人吧""对面是人吗"），关键词规则覆盖不全。

### 3.3 v2 改进

- 数字护栏：去掉证据中的列表序号；单位必须一致；数字所在语境（前 24 字、后 8 字、句首主题）须与证据有共同词；客户用语与条款用语建立同义映射（"一般住院"↔"一般医疗"、"重疾"↔"重大疾病"等）；**查表得到的结构化数字（报价、年龄段、用户自述年龄）按数值放行**，不做语境匹配。
- 缺口和合规：先去掉"能不能/是否/如果/以……为准/不能保证"等谨慎和否定表述，再判断是否给了结论；病史问题改为"健康相关词 + 买/保/报"的组合识别。
- 身份：改为"指向对方的词 + 身份词 + 疑问语气"的组合，并排除"转人工""机器人手术"等。

### 3.4 v2 结果

| 指标 | 开发集 | 保留集 1 | **保留集 2（未见过）** |
|---|---|---|---|
| 正确回答被误拦 | 0/5 | 0/5 | **0/6** |
| 数字篡改拦截率 | 94.4%（51/54） | 97.7%（43/44） | **97.7%（43/44）** |
| 缺口拦截 召回 / 精确 | 100% / 100% | 100% / 100% | **100% / 100%**（13 例） |
| 禁用表述正确率 | 100% | 100% | **100%**（6 例） |
| AI 身份 召回 / 误报 | 100% / 0 | 100% / 0 | **100% / 0**（16 例） |

**仍然拦不住的**：同一责任内两个合法数字互换，例如 ICU 津贴"单次最多 30 天"写成"60 天"（60 天是同一责任的年累计上限），或者把"26 到 30 岁"写成"26 到 31 岁"（31 是下一档的边界）。规则无法区分这类错误。

### 3.5 结论与对方案的修改

1. **规则护栏可以作为快速第一道检查，但单靠规则不够**：v1 在新问法上的表现说明，规则只能覆盖写规则的人想到的说法。保留集 2 的结果虽好，但样本小（每类 6–16 例）且与规则出自同一人之手，不能代表真实 LLM 输出上的效果。
2. **方案修改**：
   - 缺口结论、禁用表述、身份识别采用"**规则快检 + LLM 判别复核**"两层；
   - 价格、保额、免赔额、天数等**高风险数字不让 LLM 自由书写**，由查表结果按模板填入（例如"单次最多{单次天数}天，一年最多{年累计天数}天"），从源头消除数字互换。

## 四、实验 2（检索部分）：条款检索

**做法**：语料为保障计划表每个单元格 + 投保须知 + 责任免除，按行切片，共 353 段，每段带出处。用客户口语写了 40 个问题，人工标注应命中的责任项或条款关键词。对比四种方法。

**结果**：

| 方法 | hit@1 | hit@3 | hit@5 | MRR@10 | 单次检索耗时 |
|---|---|---|---|---|---|
| BM25（字二元组） | 42.5% | 55.0% | 60.0% | 0.50 | 0.3 ms |
| TF-IDF（字 1–3 元组） | 52.5% | 70.0% | **75.0%** | **0.62** | 1.1 ms |
| BM25 + TF-IDF 融合 | 45.0% | 57.5% | 60.0% | 0.52 | 1.3 ms |
| 融合 + 同义改写 | 47.5% | 60.0% | 65.0% | 0.56 | 1.5 ms |

**典型失败**：

| 客户说法 | 条款用词 |
|---|---|
| 以前就有的病能报吗 | 既往症 |
| 生孩子的费用报不报 | 分娩 |
| 看牙能报吗 | 牙科疾病 |
| 得了抑郁症住院能报吗 | 精神和行为障碍 |
| 多大年纪可以买 | 被保险人年龄 |
| 能不能多买几份 | 限投保 1 份 |

**结论与对方案的修改**：

1. 字面检索对口语问题明显不够，**必须加入语义向量检索（阿里云百炼文本向量）和 LLM 查询改写**（把"以前就有的病"改写成"既往症"），接入 API 后复测。没有用这 40 个问题手工扩充同义词表，因为那等于对着测试题调优。
2. 融合反而不如单独 TF-IDF：BM25 太弱时会把融合结果拉低。融合只在两路检索都有一定水平时才有意义，接入语义向量后重新评估融合方式。
3. 失败集中在**免责和投保条件**，恰恰是最关键的部分。方案中"高频问题配置固定条款引用"的备选方案应**升级为主方案**：既往症、等待期、补偿原则、医院范围、投保年龄、职业、一人一份、生效时间等高频关键主题，由意图识别直接定位到固定条款，不经过检索。
4. 检索耗时在 2 ms 以内，本地检索不是时延瓶颈。

## 五、实验 4（部分）：句级流式播报与 TTS 首包

### 4a 离线：LLM 输出多少字后才能开始播

| 回答 | 总字数 | 第一段可播时已输出字数 |
|---|---|---|
| 题 a | 100 | 9 |
| 题 b | 124 | 7 |
| 题 c | 45 | 6 |
| 题 d | 45 | 19 |
| 题 e | 127 | 5 |
| 首句很长的回答 | 85 | 有软切分 61 / 无软切分 85 |

句级切分让播报在 LLM 输出 5–19 个字后就能开始，而不必等全文；长首句时 60 字软切分能提前切出第一段。

### 4b 联网：edge-tts 首个音频包时延（每项 3 次取中位数）

> edge-tts 是免费的微软云端 TTS，作为阿里云 TTS 接入前的替身，绝对值仅供参考。

| 回答 | 整段合成：首包 | 整段合成：完成 | 只合成第一句：首包 |
|---|---|---|---|
| 题 a | 0.98 s | 1.51 s | 1.01 s |
| 题 b | 0.97 s | 1.50 s | 1.15 s |
| 题 c | 1.01 s | 1.42 s | 1.03 s |
| 题 d | 1.04 s | 1.44 s | 1.00 s |
| 题 e | 1.13 s | 1.94 s | 1.01 s |

**发现**：

1. 首包约 1 秒，**与文本长短几乎无关**，主要是每次调用新建连接的开销；服务本身已经是流式输出。句级切分的收益在于不用等 LLM 写完，而不在于 TTS 本身变快。
2. 按"句尾判断 0.5–0.7 s + 首句车道 ≤0.8 s + TTS 首包约 1 s"估算，首响约 2.3–2.5 s，**满足赛题 3 秒但达不到方案自定的 2 秒目标**。

**对方案的修改**：

- **承接语音频预合成并缓存**：首句车道只输出少量固定的中性承接语，可以全部预先合成，现场直接播放本地音频，首句不再经过 TTS 网络调用。
- **TTS 保持长连接、连接复用**，避免每句话都新建连接。
- 接入阿里云流式 TTS 后复测首包时延。

## 六、实验 5（离线部分）：打断逻辑

### 5a 语义层：附和还是真打断

25 个附和（"嗯""好的""对对"）、25 个真打断（"等一下""我没有社保""那月缴多少"）。

| 版本 | 附和被误判为打断 | 真打断识别率 |
|---|---|---|
| 初版 | 8%（"嗯，好的""对的"） | 100% |
| 修正后 | 0% | 100% |

> 修正是针对这组用例做的，修正后的结果不代表未见数据上的效果。

### 5b 防回声：用"与当前播报的相似度"过滤

模拟免提时 ASR 把 Agent 自己的声音识别回来：从 10 句播报中随机截取片段并加入不同程度的识别噪声（每档 300 例）；同时把 25 句真实用户插话与每句播报配对（250 对），检查是否被误当成回声。

| 阈值 | 回声拦截（无噪声） | 回声拦截（轻噪声） | 回声拦截（重噪声） | 用户插话被误删（修正前） | 用户插话被误删（修正后） |
|---|---|---|---|---|---|
| 0.4 | 100% | 99% | 96% | 4.4% | 2.4% |
| 0.5 | 100% | 99% | 92% | 3.2% | 1.6% |
| **0.6** | 100% | 98% | 73% | 0.4% | **0%** |
| 0.7 | 100% | 96% | 53% | 0% | 0% |

**发现一个严重问题**：Agent 正在说"有社保的话，基础版一年 318 元……"时，用户说"**我没有社保**"，相似度达到 0.6，会被当成回声丢掉——而这正是赛题最看重的"打断并纠正"。原因是纠正语天然会重复 Agent 的用词，只多了一个否定词。

**修正**：用户话里出现播报中没有的否定或纠正词（"没有""不是""不对"等）时，一律不按回声处理。修正后阈值 0.6 下误删为 0。

**结论**：文本相似度过滤在重噪声下只能拦住约 73% 的回声，**只能作为声学回声消除（AEC）的补充**，不能替代。

### 5c 取消与播报账本

模拟流式生成（约每 20 ms 一句）和播放（约每字 10 ms），在随机时刻插入用户打断"我没有社保"，然后按新条件重新报价。共 300 次。

| 检查项 | 结果 |
|---|---|
| 打断时刻分布 | 开口前 10 次、播报中途 182 次、整段播完后 108 次 |
| 账本正确（已播是回答的前缀、已播和作废不重叠、二者合起来连续） | 300/300 |
| 旧回答的句子在打断后被播出 | 0 |
| 取消后旧任务仍产生输出 | 0 |
| 按新条件重新报价正确（679 元 / 每月 67 元） | 300/300 |
| 打断后又说出旧价格 | 0 |
| 进程内取消耗时 | 中位数 0.036 ms，P99 0.072 ms |

**结论**：取消机制和播报账本的逻辑正确，进程内取消耗时可以忽略。**真实停播时延**主要取决于 VAD 判定（设计为 300 ms）和客户端音频缓冲，需要接入音频链路后用录音测量。

## 七、实验 6（部分）：报价所需条件的抽取

30 句口语，用例在运行前写好，运行后未改规则。

| 条件 | 正确率 |
|---|---|
| 年龄 | 15/18 |
| 有无社保 | 11/12 |
| 缴费方式 | 5/5 |
| 为谁投保 | 10/10 |
| 性别 | 9/9 |
| **整句全部正确** | **26/30** |

**失败的 4 句**："我父母都七十了还能买吗""我二十九""我妈五十八了"（口语年龄不带"岁"）、"没买过社保"。

**结论与对方案的修改**：规则抽取能覆盖常见说法，但口语变化多。方案改为：**由 LLM 抽取条件，规则作为兜底**；年龄、有无社保这类决定价格的关键条件，**报价前复述确认**（"您是 29 岁、有社保，对吧？"）。复述确认还能纠正语音识别错误。

## 八、实验发现对方案的修改汇总

| 发现 | 来源 | 方案修改 |
|---|---|---|
| 费率表含续保价，按表报价会给不能投保的人报价 | 实验 1 | 资格规则以投保须知为准，报价引擎单独校验 |
| 规则护栏在新问法上效果差 | 实验 3 | 规则快检 + LLM 判别复核 |

| 口语年龄抽取失败 | 实验 6 | LLM 抽取条件；关键条件报价前复述确认 |

## 十二、实验 2：端到端问答准确率

### 12.1 做法

- **测试集**：76 题（开发集 51、保留集 25），覆盖保障、加油包、价格、投保条件、免责、数据缺口、身份。标准依据全部来自赛题数据，**在编写问答流水线之前写好**；每 3 题取 1 题为保留集，编写时固定。题量少于方案计划的 200 题。
- **对比**：
  - **本方案**：快模型理解（意图、条件、相关责任、关键主题、缺口）→ 报价查表 / 责任表 / 固定条款 / 语义 + 关键词检索 → 慢模型生成 → 护栏（不通过重写一次，仍不通过用模板）。
  - **纯 RAG**：语义 + 关键词检索取 6 段（语料中加入费率表文本），大模型直接回答，无查表、无护栏。
- **判定**：回答须包含全部要点、不得出现禁止表述（正则判定）；保留集再做**人工复核**。
- **调整纪律**：共调整两轮，每轮只看开发集的错误；保留集只看汇总数字，调整结束后才查看保留集错误用于分析。

### 12.2 结果

| 轮次 | 本方案 开发集 | 本方案 保留集 | 纯 RAG 开发集 | 纯 RAG 保留集 |
|---|---|---|---|---|
| 第 1 轮 | 82.4% | 80.0% | 56.9% | 64.0% |
| 第 2 轮 | 92.2% | 88.0% | 56.9% | 64.0% |
| 第 3 轮（最终） | 100% | **88.0%** | 54.9% | **64.0%** |
| 第 3 轮，保留集人工复核后 | — | **80.0%（20/25）** | — | **44.0%（11/25）** |

开发集达到 100% 主要是针对开发集调整的结果，**应以保留集为准**。

| 指标（第 3 轮，全部 76 题） | 本方案 | 纯 RAG |
|---|---|---|
| 对缺口问题给出结论（如"高血压可以投保""到期可以续保"） | **0** | 9 |
| 禁用表述 | 0 | 3 |
| 文本回答耗时 P50 | 2.3–2.5 s | 1.1 s |

按类别（第 3 轮，全部 76 题，正则判定）：

| 类别 | 本方案 | 纯 RAG |
|---|---|---|
| 价格 | 93% | 60% |
| 保障 | 94% | 67% |
| 加油包 | 100% | 64% |
| 投保条件 | 100% | 67% |
| 免责 | 100% | 90% |
| 数据缺口 | 90% | **10%** |
| 身份 | 100% | 0% |

### 12.3 开发集调整中发现并修正的问题

| 问题 | 修正 |
|---|---|
| "门诊看病能报吗"含"病"和"报"，被当成疾病核保问题误拦 | 缺口判断以理解模型为主，规则只认"我有……病""做过……手术"等明确自述 |
| "职业病""先天性疾病能报吗"被当成核保问题 | 理解提示中区分"问某类疾病在不在保障范围"（免责）和"说自己患病问能不能买"（核保） |
| 产品名"百万医疗"被数字护栏当成金额 100 万 | 数字提取跳过"百万""千万"这类词语 |
| "一共保多少"没有引用总保额 600 万 | 新增"总保额"固定引用 |
| 特需病房属于加油包，回答未说明 | 生成规则：涉及加油包时说明需另外选购 |
| 数字护栏误拦后只能回答"转专员" | 改为用保障计划表字段直接拼出模板回答 |
| 判定规则本身的错误 2 处（"多大年纪"未计入、"不是什么病都能报"被当成违规） | 修正判定规则（不是流水线问题） |

### 12.4 保留集错误分析（调整结束后查看，未再据此修改）

| 题目 | 问题 | 类型 |
|---|---|---|
| 住院报销比例是多少 | 只说 100%，漏了未用社保结算时 60% | 回答不完整 |
| 全家五口人一起买优惠多少 | 被当成报价，反问年龄，没有回答家庭单优惠 20% | 理解路由错误 |
| 医保报销的部分能算进 1 万免赔额里吗 | 缺口部分处理正确，但另外说了"门急诊费用不参与累计"——这是家庭共享免赔额加油包的规则，被错套到基础版 | **跨责任混淆** |
| 我 30 岁有社保，按月交每月多少（正则判对） | 说"和互联网药品费用共享 1 万免赔额"，实际是与门急诊共享 | **跨责任混淆** |
| 保险期间是多久（正则判对） | 说"住院保障从等待期 30 天后开始"，忽略了意外无等待期 | 表述不准确 |

**最主要的剩余问题是"跨责任混淆"**：证据里同时有多项责任时，模型会把 A 责任的规则套到 B 责任上。数字护栏只能检查数字有没有依据，查不出这种错误。

### 12.5 结论与对方案的修改

1. 查表 + 固定引用 + 护栏的设计，相比纯 RAG 在保留集上高出 24 个百分点（正则判定）或 36 个百分点（人工复核），**对缺口问题给结论的次数从 9 次降到 0 次**——这是赛题"安全兜底、无编造"的核心。
2. 人工复核后保留集 80%，**未达到 90% 的目标**。下一步：
   - **证据按责任分组**，每组标明所属责任和是否加油包，生成时要求每句话只引用一组；
   - 增加**句子级事实核对**：用快模型检查每句话的主语（哪项责任）与引用证据是否一致；
   - 测试集扩充到 200 题以上，并加入多轮对话题。
3. 判定规则本身有误判（多判对和多判错都有），**最终结果必须人工复核**。

## 十三、实验 4：端到端语音时延

### 13.1 做法

用阿里云 TTS 合成 8 句"用户语音"（男声，覆盖报价、病史、免赔额、保障范围、价格变化、身份、等待期、加油包），按实时速度推给腾讯云实时 ASR；ASR 给出整句结果后：

- 立即播放**本地预合成的承接语**"好的，我帮您看一下。"（规则选择，不调用模型；身份问题直接回答，不加承接语）；
- 同时运行慢思考流水线，回答通过护栏后交给**持久连接**的 TTS（女声）逐句合成；
- 按真实时间把用户和 Agent 的音频放进**双声道录音**（左：用户，右：Agent），保存时间轴。

所有时延**从用户说完话算起**（按音频能量判断语音结束），与官方用录音验收的口径一致。每个版本 8 句 × 2 轮 = 16 轮。

### 13.2 单项服务

| 服务 | 结果 |
|---|---|
| 阿里云流式 TTS，持久连接 | 建连 0.23 s（一次）；每句首包约 0.2 s（对比 edge-tts 每次新建连接约 1 s） |
| 腾讯云实时 ASR | 句尾判定（用户说完 → 整句结果）P50 0.45 s，最大 0.52 s；用户还在说时已陆续返回中间结果，例如"我三十岁有社保"在说完前约 1 s 就已识别 |
| 理解（qwen-flash） | 约 0.3–0.5 s |
| 查询改写（qwen-flash） | P50 0.28 s |

### 13.3 三个版本对比

| 版本 | 做法 |
|---|---|
| v1 | 流式生成，逐句过护栏、逐句播放 |
| v2 | 语音模式：提示词要求 50 字以内，整段回答过护栏后再播放 |
| v3 | 在 v2 基础上：**程序强制**截断到 50 字（保留完整句子前缀，被截时追问"要不要我接着说说"）；报价话术精简；TTS 语速 1.15 倍 |

| 指标（从用户说完算起） | v1 P50 / P90 / 最大 | v2 P50 / P90 / 最大 | v3 P50 / P90 / 最大 | 赛题要求 |
|---|---|---|---|---|
| **首响**（承接语开始播放） | 0.46 / 0.65 / 0.93 s | 0.46 / 0.62 / 0.75 s | **0.45 / 0.65 / 0.65 s** | ≤3 s ✅ |
| 第一句实质回答开始播放 | 2.41 / 3.45 / 3.83 s | 3.05 / 3.94 / 3.98 s | 2.98 / 4.16 / 4.39 s | — |
| **完整回答音频生成完毕** | 4.31 / 5.79 / 6.34 s | 4.69 / 5.74 / 6.22 s | **4.37 / 5.70 / 6.06 s** | ≤10 s ✅ |
| Agent 把整段话说完 | 16.8 / 25.6 / 33.9 s | 14.8 / 21.0 / 25.0 s | **13.0 / 16.0 / 18.6 s** | 见下文 |

### 13.4 发现

1. **首响远低于 3 秒**。承接语预合成后，首响只取决于 ASR 句尾判定（约 0.45 s），不再受模型和 TTS 网络时延影响。
2. **完整回答在 6.1 秒内全部生成**，满足"≤10 秒"。
3. **但如果按"Agent 把话说完"计算，一段完整回答很难在 10 秒内说完**：TTS 语速约每秒 4 个字，10 秒只能说 40 字左右，再加上承接语约 2 秒和等待回答的 2–3 秒。这取决于官方对"完整回答≤10秒"的口径，需要确认。
4. **v1 逐句过护栏、丢弃不通过的句子，会让剩下的话前后不接**：例如丢掉了"首先，1万元是年度免赔额"，剩下"其次……最后……"；丢掉一句后剩下以"但"开头。v2 起改为整段过护栏再播放。
5. **提示词限制字数不可靠**：v2 要求 50 字以内，模型仍写出 82 字、108 字的回答，v3 改为程序截断。
6. **产品名"2026版"被数字护栏当成无依据数字**，已加入白名单。
7. **报价被重复**：报价引擎说过之后模型又说一遍，v2 起删去与报价金额重复的句子。

### 13.5 语音模式的准确率代价

用实验 2 的 76 题，在语音模式（程序截断 50 字）下重测：

| 模式 | 开发集 | 保留集 | 缺口给结论 | 文本回答耗时 P50 |
|---|---|---|---|---|
| 文本模式（约 100 字） | 100% | 88% | 0 | 2.3–2.5 s |
| 语音模式（50 字） | 90.2% | 80% | 0 | 2.0 s |

保留集下降约 8 个百分点，原因有两类：一是确实丢了关键信息，例如 v3 录音中"我自己先掏一万，剩下是不是全报"被答成"免赔额以保单约定为准"；二是测试题要求一次说出 2–3 个要点，而语音模式故意只说一两点、再问"要不要我接着说说"，单轮判定会把留到下一轮的内容算作错误。**要公平评估语音模式，需要多轮对话测试题**。

### 13.6 对方案的修改

| 发现 | 修改 |
|---|---|
| 承接语预合成后首响约 0.45 s | 首句快车道由"小模型生成承接语"改为"规则选择预合成承接语"，小模型只用于理解 |
| 持久连接 TTS 首包约 0.2 s | TTS 必须用持久连接 |
| 逐句丢弃会让回答前后不接 | 短回答整段过护栏后再播放；不通过则整段重写或用模板 |
| 提示词控制字数不可靠 | 语音回答由程序按句截断，被截时追问是否继续 |
| 报价确定，可最先说 | 报价由报价引擎直接播报，模型只补充，不重复金额 |
| 一段话说完往往超过 10 秒 | 一次只讲一两点、多轮展开；需向官方确认"完整回答≤10秒"的计算口径 |
| 语音模式准确率下降 | 关键纠正类问题（如"是不是全报"）的核心结论用模板给出；补充多轮测试题 |

## 二十二、真实音频打断

### 22.1 方案（参考 LockedIn 的实现）

LockedIn 的做法：

| 环节 | LockedIn 做法 | 本方案改动 |
|---|---|---|
| 触发 | 播放中只要收到候选人的转写就立即停播（`AudioPlayer.interruptAudio`），不区分附和 | 先降低音量继续听，第一段识别结果出来后由"规则快路径 + 小模型"判断附和还是打断 |
| 防回声（主） | 播放期间直接屏蔽语音采集（L2，`speakerMode` / `micPauseWhileSpeaking`） | 全双工不能屏蔽采集，改为**声学回声消除（AEC）**：浏览器 `getUserMedia` 开启 `echoCancellation`，电话侧用运营商/网关 AEC |
| 防回声（兜底） | 识别结果与最近播报内容的实词重合度超过阈值即丢弃（L1，`isProbablyEcho`，带时间窗） | 保留，增加豁免：含纠正词或疑问词的句子不当作回声 |
| 自打断保护 | 朗读模式下播放期间不响应打断（`guardBargeInWhileSpeaking`） | 作为"无 AEC 环境"的降级方案 |
| 服务端 | 新回答开始即重置音频流；会话停止时中止生成（`cancel_event`） | 打断即取消慢思考任务；播报账本记录已说 / 未说 |

代码：`src/agent/dialogue.py` 中的 `BargeInController`。

### 22.2 测试

Agent 播放一句回答，1.0–2.5 秒时用户插话；麦克风信号 = 用户语音 + Agent 播报泄漏（"有回声消除"取 3% 音量，"无回声消除"取 30%）+ 底噪，按实时速度推给腾讯云实时 ASR。每种条件 8 句真打断、6 句附和、4 次只有回声。

| 条件 | 真打断成功停播 | 停播时延（从用户开口算） | 附和被误停 | 只有回声时被误停 |
|---|---|---|---|---|
| **有回声消除** | **8/8** | P50 **0.79 s**，最大 1.68 s | **0/6** | **0/4** |
| 无回声消除 | 8/8 | P50 1.09 s，最大 1.96 s | 6/6 | 4/4 |

**结论**：

1. 有回声消除时，打断全部成功、附和与回声都没有误停，停播时延中位数 0.79 秒（主要是语音识别出第一段结果的时间）。
2. **没有回声消除时系统不可用**：Agent 自己的声音被识别成"高血压属于""重大疾病"等片段，文本层兜底虽能挡掉前几段，但最终仍会误停。和 LockedIn 的经验一致——回声主要靠声学层解决，文本匹配只能兜底。
3. 样本量小（每类 4–8 例），只能作为初步验证；用户语音为合成语音。

| 最多 3 步 | 86.7% | 66.7% | 2.1 | 6.3 / 9.5 / 11.8 s |
| **最多 5 步** | **93.3%** | **70.0%** | **2.3** | 5.9 / 9.0 / 12.0 s |
| 最多 5 步、时间预算 3 秒 | 70.0% | 53.3% | 2.0 | 6.9 / 15.0 / 44.4 s |

保留集 10 题人工复核：固定路由约 7/10，最多 5 步约 9/10（其中 1 题 5 步模式只给了兜底话术、反而更差）。

**发现**：

1. 允许 5 步时 Agent **平均只用 2.3 步**——它判断够了就停，上限主要用来防止失控。
2. 复合问题上，叠 step 比固定路由更完整（自动判分 +20 个百分点，人工复核 +2 题），代价是耗时 P50 增加约 2 秒，最慢超过 10 秒。
3. "3 秒预算"的配置效果最差且出现 44 秒的极端值：预算截断了 Agent，而接口超时没有真正生效（本轮与大链路实验并发运行，限流重试也拉长了耗时）。
4. 本轮耗时受并发负载影响偏高，需要单独复测。

**结论**：步数上限不是关键，**"什么问题走 Agent"才是关键**——简单问题走固定路由（快、准），只有理解层判断为多处依据的复合问题才开启 Agent；上限可以设 5 步，同时必须加**真正生效的硬截止时间**（到点用已有依据回答），工具调用尽量并行。

## 二十四、大链路：整通电话

DeepSeek 扮演 12 类用户（每类有隐藏的年龄、社保、病史和态度，以及必须做的事），每类 2 通，共 24 通，最多 14 轮。程序自动检查 + 人工逐通阅读全部记录。

### 24.1 自动检查（程序判定的硬指标）

| 检查项 | 结果 |
|---|---|
| 开场说明 AI 身份和录音 | 24/24 |
| 最终报价与用户真实条件一致（直接读 CSV 比对） | 15/15 |
| 纠正信息后重新报价（如 423 → 971 元） | 2/2 |
| 发投保链接前门禁齐全（已报价、已提示限制、已提示如实告知、用户同意） | 4/4 |
| 两次拒绝后礼貌结束、不再推销 | 2/2 |
| 要求人工时转人工 | 2/2 |
| 禁用表述 | 0 次 |
| 每轮耗时（文本，不含 ASR/TTS） | 各通中位数的中位数 1.9 s，最大 6.6 s |

### 24.2 自动审阅也不可靠

- 程序检查里的"缺口不下结论"对**每一轮**都调用了小模型复核，而该复核对普通问题有约 17% 的误拦，"门诊能报吗 → 能报"也被计为违规，这一项（12/24）不可信。
- 改用 DeepSeek 逐轮审阅 112 轮：它把"续保以条款为准""您有没有正在治疗的疾病"判为违规，把资料里有的"ICU 每天 500 元"判为编造，把"我是众安保险的AI助理"判为没回答身份问题。

**最终以人工逐通阅读为准。**

### 24.3 人工阅读发现的问题

| 问题 | 涉及通话 | 原因 |
|---|---|---|
| 不必要的转人工 | 6/22（不含主动要求人工的 2 通） | 风险计数每轮都加：用户追问续保、带病史的上下文都会再计一次，2–3 轮就转人工；且转人工话术与回答拼接错乱 |
| 用户的问题被跳过（病史、免赔额、"保些什么"） | 约 6 通 | 一句话里既有信息又有提问时被判为"提供信息"；或流程的追问抢在回答前面 |
| 问完身份后丢失刚说的年龄，反复问年龄 | 2 通（两位用户都因此挂断） | 身份分支跳过了条件抽取 |
| "我觉得有医保就够了"被当成身份询问 | 2 通 | 理解误判 |
| 用户说"好的，发过来吧"，系统又问一遍，没有发链接 | 1 通（丢单） | 没识别出同意 |
| **对数据缺口给了结论**（"医保报完剩下的扣1万再报"） | 2 通 | 未识别为"社保报销能否计入免赔额"的缺口 |
| **承诺做不到的事**（"发您微信"） | 2 通 | 没有按系统能力检查承诺 |
| 重复句子（社保问两遍、如实告知说两遍） | 3 通 | 流程追问与回答没有去重 |
| 模板选错（问优惠答成家庭共享免赔额加油包） | 1 通 | 兜底模板取错责任 |
| 挽留话术对无社保用户说"有社保几百元" | 1 通 | 挽留话术写死 |

24 通中完全没有问题的约 9 通。结局：发投保链接 4 通、转人工 8 通（其中 6 通不必要）、用户拒绝结束 2 通、用户挂断或轮数用尽 10 通。

### 24.4 结论：设计合不合理

| 层 | 结论 |
|---|---|
| 大链路的**结构**（状态机 + 程序门禁 + 固定合规话术） | **合理**：所有由程序把关的硬指标全部通过——报价、门禁、合规声明、拒绝处理、转人工请求没有一次出错 |
| 大链路的**每轮调度策略** | **不合理，需要重做**：回答和推进的先后、身份分支、同意识别、风险转人工的计数方式、去重都有缺陷；这些是"程序怎么调度模型"的问题，不是模型能力问题 |
| 小链路 | 简单问题走固定路由合理；复合问题需要 Agent 叠 step，但必须按问题复杂度分流并加硬截止时间 |
| 自动评测 | 两种自动审阅（规则、DeepSeek）都有大量误判，正式结论必须人工复核 |

### 24.5 下一步修改

1. **每轮先回应、再推进**：只要用户这句话里有提问，先回答，再接流程追问；流程追问与回答去重。
2. **身份分支不跳过条件抽取**；身份判定需规则或两个模型一致。
3. **同意识别**：用户说"发过来""好的发我"等，在投保阶段直接视为同意。
4. **转人工改为"询问 + 主题去重"**：同一缺口主题只计一次；达到阈值时先问用户"要不要帮您转专员"，不直接转。
5. **能力护栏**：回答里出现系统没有的动作（发微信、寄资料、给额外折扣）即拦截。
6. **缺口识别补强**："医保报完的还能不能报 / 剩下的怎么报"归入"社保报销能否计入免赔额"。
7. 挽留话术按用户画像填写，不写死。
8. 小链路按复杂度分流到 Agent，硬截止时间真正生效；单独复测耗时。

### 26.3 原因

| 问题 | 原因 |
|---|---|
| 未经同意发链接 | 同意判断把句首的"嗯"当成肯定，"嗯……那我再考虑考虑吧，先挂了"被判为同意 |
| 同意后又重新问 | 用户同意时门禁未满足（还没提示如实告知），系统先提示如实告知，但没有记住"用户已同意"，下一轮又问一遍 |
| 缺口兜底误触发 | 只看当前句的缺口检测过于敏感，"网上买药能报吗""72 岁还能买吗"都被判为缺口；且误判的缺口类型不对（报价问题答成续保话术） |
| 承诺回电、发条款 | 能力护栏只覆盖了"发微信/寄资料"等说法 |
| 加油包价格 | 报价引擎支持加油包，但大链路没有接入加油包报价 |

### 26.4 结论

- **调整有效的部分**：强制转人工、身份分支丢条件、发微信等第五轮问题已基本消除；硬指标（报价、超龄、身份、拒绝、转人工）全部通过。
- **出现了更严重的新问题**：未经同意发链接违反门禁，必须最先修复；"同意"状态需要在门禁之后保留。
- **缺口检测在"漏判"和"误判"之间摇摆**：带历史判断会"粘住"，只看当前句又过于敏感。需要在二者之间取舍：当前句检测 + 理解模块交叉确认，且只在两者一致或规则命中时才走兜底。
- 小链路单轮准确率在全新保留集上为 83.8%（人工复核），仍未达到 90%；最主要的可修问题是"报价后自行补充的保障介绍"。

### 26.5 下一轮修改

1. 同意判断：只接受明确肯定（"发吧""发过来""可以发""好的发我"），带"考虑、想想、再说、先挂、商量"的一律不算；门禁未满足时记住"已同意"，门禁满足后直接发链接。
2. 缺口兜底：当前句检测与理解模块一致、或规则命中时才触发；兜底话术按检测到的缺口类型选取。
3. 报价类回答只用程序生成的报价句，不让模型补充保障介绍。
4. 能力护栏补充"条款发给您""回电""查到后联系您"等说法。
5. 接入加油包报价。
6. 去重时忽略"您"等虚词差异。

## 二十七、端到端语音时延重测（第六轮版本）

第三轮之后加入了小模型事实核对、复合问题 Agent、大链路（理解 + 对话作用 + 缺口检测三路并行、流程话术），一直没有重测。本次用当前版本重测：第三轮的 8 类问题 + 4 道复合问题，各 2 轮，共 24 轮；流程与第三轮相同（TTS 合成用户语音 → 腾讯云实时 ASR → 预合成承接语 → `CallSession.turn` → 持久连接 TTS），时延从用户说完话算起。

第一次测出两个设计缺陷后修正并再测一次，两次结果都保留：

| 指标 | 第三轮（旧版本） | 第六轮版本 | 修正后 |
|---|---|---|---|
| 首响（承接语开始播放） | P50 0.45 s | P50 0.44 s，最大 0.52 s | P50 0.48 s，最大 0.51 s |
| 回答文字生成完 | — | P50 4.9 s，最大 10.7 s | P50 5.6 s，最大 12.0 s |

第一次修正的两个缺陷：

1. 复合问题判断过宽，"我三十岁，有社保，一年多少钱"这样的报价问题也开启了 Agent（跑了 4 步、10.7 s）。改为报价/优惠/身份问题不走 Agent，且需要至少 2 项责任或 2 个独立问句。
2. 缺口拦截的旧关键词规则把"得了癌症……能报吗"当成疾病核保问题拦截，既多一次重写又把正确回答换成了兜底话术。改为大链路已判定缺口时只按判定结果拦截。

修正后整体几乎没有改善，逐轮拆解后发现主要耗时在：

| 来源 | 耗时 | 说明 |
|---|---|---|
| **小模型事实核对** | 每次约 1–2 s（逐轮诊断运行中测得，结果 JSON 未保存分段耗时；第七轮单独测 qwen-flash 核对 P50 0.38 s、P90 1.24 s） | 不通过时重写再核对，"免赔额"一题共 7.4 s，其中生成约 2.7 s、两次事实核对约 4.5 s；且核对过严，把"看病要用社保结算"判为无依据，把正确回答换成了模板 |
| 回答过长 | 合成 3–7 s | 回答本身截到 50 字，但大链路在同一轮又附加了流程话术（提示限制约 45 字、如实告知约 40 字），总长 71–156 字；逐句合成串行进行 |
| Agent | 每步约 3 s | 复合问题触发 1 步就多 3 s |
| 理解（三路并行） | 0.9–2.1 s | 以最慢的一路为准 |

**结论**：首响不受影响；但当前版本的复杂回答**不满足 10 秒**。第三轮能达标是因为当时没有事实核对、没有 Agent、回答也没有附加流程话术。准确率措施（事实核对、Agent）与时延之间需要重新取舍：

1. 事实核对只在回答涉及多项责任或含高风险数字时运行，并与第一句的语音合成并行；核对提示词放宽，只拦"说错"，不拦"换了说法"。
2. 流程话术不和回答放在同一轮：本轮有实质回答时，流程话术留到下一轮。
3. 生成与合成流水线化：模型流式输出每出一句就送 TTS，不等整段文字生成完；可再用多条连接并行合成。（第八轮更正：测试中合成本来就与播放重叠，原写"第一句播放时合成后面的句子"不准确。）
4. Agent 一步约 3 s，复合问题优先用"理解层选出的多项责任一次性取齐依据"的确定性方式，Agent 只作补充。
5. 修改后重测，并把"回答文字生成完"和"音频全部合成完"都作为验收口径记录。

# 第七轮：模型对比（qwen vs DeepSeek）

> 系统此前全部使用通义千问：小模型环节 `qwen-flash`，回答生成 `qwen-plus`；DeepSeek 只用于测试侧（扮演用户、判分、改写题目）。
> 本轮在百炼上可用的 DeepSeek 模型：`deepseek-v4-flash`、`deepseek-v4-pro`、`deepseek-v4.1-flash`、`deepseek-v3.2`，均支持 JSON 输出、流式和工具调用。
> 所有环节都用已有的标注集打分，提示词与流程完全相同，只换模型。

## 二十八、小模型环节

| 环节（测试量） | qwen-flash | deepseek-v4-flash | deepseek-v4.1-flash | deepseek-v3.2 |
|---|---|---|---|---|
| 打断：附和误判 / 真打断识别（240 句） | 0% / 100% | 0% / 98.3% | 0% / 100% | 0% / 100% |
| 条件抽取：年龄 / 社保（200 句） | 100% / 100% | 100% / 100% | 100% / 100% | 100% / 100% |
| **缺口检测**：召回 / 误报（275 题） | 98.2% / **21.3%** | 100% / 22.6% | **100% / 8.6%** | 75.9% / 5.9% |
| 身份识别：召回 / 误报（176 例） | 100% / 0% | 97.7% / 0% | 100% / 2.2% | 100% / 2.2% |
| 缺口复核：召回 / 误拦（380 例） | 100% / 7.1% | 100% / **0%** | 100% / 2.2% | 100% / 0.5% |
| **事实核对**：错误回答拦下 / 正确回答误拦（80 个人工判定过的回答） | 4/13 / 10/67 | 3/13 / 10/67 | 9/13 / 45/67 | 8/13 / 51/67 |
| 单次调用时延 P50 | **0.23–0.42 s** | 0.68–0.92 s | 0.65–1.6 s | 0.55–3.8 s |

**发现**：

1. 打断、条件抽取、身份识别四个模型效果相当，qwen-flash 快 2–3 倍。
2. 缺口检测：deepseek-v4.1-flash 把误报从 21.3% 降到 8.6%，召回不降，是本轮最大的差别，正好对应第六轮"缺口兜底误触发"的问题。
3. 缺口复核：DeepSeek 误拦更少（7.1% → 0–2%）。
4. **事实核对换哪个模型都不行**：要么拦不住（3–4/13），要么大量误拦正确回答（45–51/67）。问题在事实核对本身的提示词和做法，不在模型。

自动判分在三个模型之间不一致的 19 题人工复核（其余 61 题三个模型都被两种判分判对，不影响比较）：

| 模型 | 19 题中人工判对 | 主要问题 |
|---|---|---|
| qwen-plus | **13** | 缺口兜底误触发多 2 次（如"喝酒打架受伤能赔吗"答成"转专员确认"） |
| deepseek-v4-flash | 12 | 把"那我爸61岁有医保呢"当成身份询问；缺口误触发 |

**结论**：

- 回答生成三个模型准确率没有实质差别，qwen-plus 最快，继续使用 qwen-plus。
- 小模型环节：继续以 qwen-flash 为主；**缺口检测**可考虑换成 deepseek-v4.1-flash（误报 21% → 9%），代价是这一路从约 0.28 s 变为约 0.67 s，而它与理解并行，每轮约多 0.4 s；也可以先改 qwen-flash 的缺口检测提示词再比较。

- 新发现的提示词问题：护栏不通过时的"重写"指令以对话形式发给模型，模型会对用户道歉（"抱歉，刚才说得不够准确"）。重写应改为独立的一次生成，不带前一版回答和批评语气。

## 三十一、真实音频打断（扩大）

脚本 `experiments/exp5_audio_v2.py`，结果 `exp5_audio_v2.json`。混音、识别、判断流程与第二十二节相同；用例全部新写：40 句真打断（纠正条件、叫停、提问、拒绝、身份、投诉）、30 句附和、8 句 Agent 播报（只有回声：每句 3 次，共 24 次）；用户语音男女两种音色交替。新增"回声消除不完全"（泄漏 10%）一档。

| 条件 | 真打断成功停播 | 停播时延 P50 / P90 / 最大 | 附和被误停 | 只有回声时被误停 |
|---|---|---|---|---|
| **有回声消除（泄漏 3%）** | **40/40** | **0.69 / 1.09 / 3.14 s** | **2/30** | **0/24** |
| 回声消除不完全（10%） | 40/40 | 1.13 / 1.80 / 2.74 s | 28/30 | 23/24 |
| 无回声消除（30%） | 40/40 | 1.38 / 2.65 / 5.41 s | 30/30 | 24/24 |

（第四轮：有回声消除 8/8、0.79 s、附和误停 0/6、回声误停 0/4。）

**发现**：

1. 有回声消除时结论成立且样本扩大 5 倍：真打断全部停播，停播时延中位数 0.69 s。
2. 附和误停 2/30（第四轮 0/6）：两例都是**识别把短附和听错**——"行行"识别成"醒醒"、"嗯嗯"后段识别成"致"，小模型把这类无意义短片段判成了打断。可修：播报中出现 ≤2 字且不含叫停词的片段时继续等后续识别结果，不立即停播。
3. **回声消除不完全（10% 泄漏）时系统已不可用**：附和与回声几乎全部误停。文本层"与播报重合"过滤只能挡住前几段，Agent 自己声音的识别片段（如"门急诊加油"）最终被判成打断。回声消除不仅是必选项，而且**泄漏要压到很低**；电话侧需实测运营商 / 网关 AEC 的残余回声水平。
4. 两种音色停播时延接近（0.66 / 0.69 s）。用户语音仍为合成语音。

### 31.1 测试侧缺陷修复

时延扩大测试第一次运行时，第 9 轮起全部失败：`RealtimeTTS` 在一次服务端错误后不清除错误状态，此后每次合成都直接报错。修复（`src/agent/cloud.py`）：每次合成前清除错误；会话出错或断开时自动重连并重试一次，重连耗时计入该轮时延，并在结果中标出（`tts_reconnects`）。

| **回答音频全部合成完** | 9.18 / 14.53 / 16.67 s，10/24 超 10 s | **8.75 / 12.76 / 16.96 s，19/60 超 10 s** | 8.31 / 10.71 / 15.20，**8/40** | 10.53 / 13.44 / 16.96，**11/20** |
| Agent 把话说完 | 21.5 / 32.0 / 34.4 s | 20.8 / 28.4 / 35.9 s | 19.8 / 25.1 / 31.3 | 22.8 / 31.8 / 35.9 |

（格式：P50 / P90 / 最大。两轮合计 84 轮：音频合成完 P50 9.0 s，29/84 超过 10 s。）

**发现**：

1. 首响稳定：60 轮 P50 0.46 s、最大 0.80 s，远低于 3 秒。
2. **复杂回答 10 秒仍不达标**，样本扩大后结论不变：按"音频全部合成完"计 19/60（32%）超过 10 秒，复合问题超过一半（11/20）。按"文字生成完"计 60 轮全部在 10 秒内（最大 9.66 s）。两种口径结论相反，官方口径必须确认。
3. 拆解：文字生成完到音频合成完中位数 4.0 s（整段文字生成完才开始合成，且一条连接逐句合成；合成与播放本已重叠，第一句实质回答在文字生成完后约 0.2 s 开播）；**49/60 轮在回答后附加了"提示限制"流程话术**，这些轮回答中位数 90 字，未附加的 61 字；开启 Agent 的 15 轮音频合成完中位数 9.9 s，未开启的 8.5 s。与第二十七节的判断一致：流程话术移到下一轮、生成与合成流水线化、复合问题少用 Agent，是三个主要可改点。
4. 本实验每轮预设"已报过价"，所以大链路几乎每轮都会推进到"提示限制"，比真实通话中的比例偏高；整通电话（第三十三节）每轮文本耗时中位数 2.1 s。

# 第九轮：去掉小模型事实核对的消融实验

> 新增开关 `FACT_CHECK`（`src/agent/pipeline.py`；实验时默认开启，本轮结束后改为默认关闭），其余代码、题目、用例与第八轮完全相同，只关掉事实核对重跑。
> 问答：`exp2_qa_v2.py --data qa_v4.json --tag v4_nofc --agent-steps 5`；时延：`FACT_CHECK=0 python experiments/exp4_e2e_v5.py _expand_nofc`（单独运行，60 轮无错误、无重连）。

## 三十五、准确率：事实核对没有可测出的作用

| | 事实核对开（第八轮） | 事实核对关 |
|---|---|---|
| 规则判分 | 80.7% | 82.7% |
| DeepSeek 判分 | 80.7% | 79.3% |
| 逐题复核（严格） | 106/150（70.7%） | 101/150（67.3%） |
| 逐题复核（边界题算对） | 111/150（74.0%） | 109/150（72.7%） |
| 文本回答耗时 P50 / P90 | 2.42 / 5.56 s | **1.66 / 4.81 s** |

- 复核差 2–5 题，小于本轮观察到的噪声：两次运行生成本身不同，且两批复核者口径不同（关掉后的第 2 批复核把"所有责任都限二级医院"等医院范围的笼统说法判为边界错，第八轮未判）。95% 区间完全重叠，**不能认为事实核对提高了准确率**。
- 第八轮开启时，事实核对在 150 题中留下记录的只有 2 题（W059、W139），**两次都是误拦**：把程序给出的正确价格（399 元、328 元）判为"资料里没有"，换成了兜底话术。
- 两种运行中的主要错误类型相同（报价后补充介绍说错、兜底误触发、加油包未报价、缺口给结论），都不是事实核对能拦下的类型。与第七轮结论一致：拦不住错误，还误拦正确回答。

## 三十六、时延

| 指标（P50 / P90 / 最大） | 事实核对开（60 轮） | 事实核对关（60 轮） |
|---|---|---|
| 首响 | 0.46 / 0.50 / 0.80 s | 0.46 / 0.52 / 1.11 s |
| 回答文字生成完 | 4.88 / 7.33 / 9.66 s | **4.21 / 6.63 / 8.41 s** |
| 回答音频全部合成完 | 8.75 / 12.76 / 16.96 s | **8.12 / 11.20 / 13.60 s** |
| 音频合成完超过 10 s | 19/60 | **15/60** |
| 其中单项问题 | 8.31 s，8/40 超时 | 7.62 s，5/40 超时 |
| 其中复合问题 | 10.53 s，11/20 超时 | 10.01 s，10/20 超时 |

- 去掉事实核对后，文字生成快约 0.7 s，音频合成完中位数快约 0.6 s，**最慢一轮从 17.0 s 降到 13.6 s**（核对不通过时的"重写再核对"长尾消失）。
- 但仍有 15/60 超过 10 s，复合问题仍有一半超时：剩下的瓶颈是整段文字生成完才开始合成、单连接逐句合成（约 4 s）、附加的流程话术和 Agent 步数，事实核对不是主因。

## 三十七、结论

**已默认关闭事实核对**（`FACT_CHECK=1` 可重新开启）：准确率上测不出收益，且已观察到误拦正确价格；关闭后时延和长尾都改善。准确率要靠第八轮列出的确定性措施（报价类回答只保留程序报价句、"ICU / 等待期"固定引用、加油包接入报价），时延要靠流程话术移到下一轮和生成与合成流水线化（模型流式输出按句送 TTS，不等整段文字）。
